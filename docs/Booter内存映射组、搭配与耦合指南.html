OpenCore 通用技术笔记 · 规则底稿 01

Booter 内存映射组
搭配与耦合指南

为什么它会让开机「卡住」，22 个开关怎么分组、怎么互相牵制，以及每种情况该开哪一个。

依据 OpenCore 1.0.8 官方文档与中文参考手册 · 初稿 2026-11-15 · 通用化修订 2026-11-16
00

先说结论

会。内存映射这一组是「开机卡住」最典型的元凶之一，而且是最难查的一种：它死在 macOS 内核能打印出任何错误信息之前，所以你看到的往往只是黑屏、苹果标停住、或者直接重启，没有报错、没有崩溃栈、日志停在半路。

官方原文：对于 RebuildAppleMemoryMap、EnableWriteUnprotector、ProtectMemoryRegions、SetupVirtualMap、SyncRuntimePermissions 这几项，「即使在相似的硬件上也没有确定的取值方法，可能必须试遍它们的各种组合」；而 SyncRuntimePermissions 的适用信号「包括黑屏卡住」。
但也别把所有卡住都算到它头上。崩点明确落在 kext / 存储驱动的详细崩溃栈、禁止符号、卡在 Still waiting for root device，通常属于 kext、ACPI 或存储驱动，而不是内存映射。判断标准是：越早死、越没输出，越可能是这一组；反过来，早期引导崩溃也可能是 SyncRuntimePermissions 的信号（见 R2），别把「有崩溃栈」当成绝对排除条件。

这一组一共多少开关

Booter → Quirks 共 22 个，其中和内存映射 / 内存分配直接相关的约 14 个；另有几个在 UEFI → Quirks、Misc → Security 里，但和它强耦合。

为什么不能照抄别人的

这些开关修的是「主板固件画出来的内存地图」和「苹果内核想读的样子」之间的差，差在哪块板子上都不一样。官方明确说没有通解。

好消息

其中一大半其实有确定的判定信号（日志关键字、固件年代、机型、是否虚拟机），只有 5 个真的需要试。第 08 节把可自动判定的部分单列出来了。

先把「不是这一组」排掉。官方给 SyncRuntimePermissions 写的适用信号很宽：既包括黑屏挂起，也包括更明显的内核崩溃，所以「有崩溃栈」不能一律排除。但下面三类仍与内存映射无关，别在这一组里空转：① 崩点明确落在第三方驱动或存储栈的完整 panic 栈；② 系统已起来、只是某个驱动或设备不工作（显示只剩基础帧缓冲、某个硬件端口消失等）；③ 某个 PCIe 设备整体不枚举，IORegistry 里连设备 ID 都找不到——那属于固件设置、板载设备开关或 ACPI 层。判据是：这一组只管「固件把内存地图交给内核」那一步，交接完成之后发生的事都往下查。
01

为什么会卡住：一次「交接」

开机时 UEFI 固件要把机器交给 macOS 内核，交出去的东西里有一张内存地图：哪一段内存是什么用途、能不能读、能不能写、能不能当代码执行。真 Mac 的固件按苹果的规矩画；PC 主板固件各画各的。XNU 内核按苹果的规矩去读，读不对就当场死掉——这时候它连初始化日志都还没来得及开。

图 1 · 交接链路：Booter Quirks 本质是「内存地图翻译器」

三个环节，对应三组开关

环节固件常犯的毛病后果负责的开关
① 地图本身地图条目太多（超过一页 4 KB）；权限表和地图对不上；相邻条目被错误合并内核解析时崩溃、用完就放的内存被误释放RebuildAppleMemoryMap
② 权限标注把 OpenRuntime 标成「不可执行」；把代码页写保护开着；内存属性表丢了条目调用 UEFI 运行时服务时崩，典型表现就是黑屏卡住SyncRuntimePermissions、EnableWriteUnprotector
③ 地址与空位低位 4 GB 被占满，找不到地方放内核；MMIO 区域被标成运行时；固件在 SetVirtualAddressMap 之后还用虚拟地址访问内存分配失败、KASLR slide 撞车、早期重启ProvideCustomSlide 一组、DevirtualiseMmio、SetupVirtualMap
一个常见误解：这些不是「性能优化开关」，全开不会更好。每一个都是针对某一种固件缺陷的补丁，开在不需要它的机器上反而会引入新问题。官方文档对一整套「全开」的老配方明确写了 strongly discouraged（强烈不推荐）。
02

22 个开关，按「解决什么问题」分四组

不要按字母顺序记。按下面的四组记，每组解决一类毛病，耦合也只发生在组内和组间少数几条线上。

先分清两个「默认值」。官方中文参考手册给每一项标的是「安全值（Failsafe）」：Booter Quirks 里布尔项几乎全是 false，整数项是 0 或 -1。它表示「配置缺项或取值不合法时回退到什么」，不是推荐值。而随包附带的 Docs/Sample.plist 是一份能开机的示例，其中 AvoidRuntimeDefrag、EnableWriteUnprotector、ProvideCustomSlide、EnableSafeModeSlide、SetupVirtualMap、FixupAppleEfiImages 都是 true。下表这一列写的是 Sample 值，只作对照基线；它与 Failsafe 不一致是常态，不要据此判断谁对谁错，更别把 Sample 当成官方推荐组合。

A 组 · 运行时权限（最常导致「黑屏卡住」）

开关一句人话Sample 值
RebuildAppleMemoryMap照着内存属性表，把整张地图重画成苹果内核能解析的样子关
SyncRuntimePermissions把地图和属性表里的「可读/可写/可执行」标记对齐，尤其是别把 OpenRuntime 标成不可执行关
EnableWriteUnprotector老办法：临时关掉 CR0 写保护，让运行时服务代码能写。会削弱固件安全性开
ProtectUefiServices有的固件（尤其 VMware、经 GRUB 链式加载）会在加载驱动时偷偷改 UEFI 服务指针，把上面几个的修正冲掉。这个负责守住关
AvoidRuntimeDefrag阻止 boot.efi 搬动运行时服务的内存；否则某些用 SMM 存 NVRAM 的固件会失灵（时间、NVRAM、关机异常）。除苹果和 VMware 外的 PC 几乎都需要开
ClearTaskSwitchBit32/64 位混合内核时清掉 CR0 的 TS 位，避免 FPU 崩溃。只关旧系统 / Hyper-V关
DisableVariableWrite禁止 macOS 写 NVRAM，安全选项；也可用来绕开固件写变量就崩的毛病关

B 组 · 虚拟地址与地图形态

开关一句人话Sample 值
SetupVirtualMap有些固件在 SetVirtualAddressMap 之后还按虚拟地址访问内存 → 早期崩。这个提前做恒等映射兜住。不兼容 32 位内核开
ProtectMemoryRegions把 CSM 区、MMIO 区标成正确的内存类型。官方说通常只有很老的固件才需要关
ForceExitBootServicesExitBootServices 失败时抓一张新地图重试。官方明说「不理解后果别用」关
DiscardHibernateMap休眠唤醒时沿用旧地图。只为极少数老 Insyde 笔记本 / 与 Windows S4 共存设计，别乱开关
ForceBooterSignature休眠唤醒时把 booter 签名换成 OpenCore 的，用在真 Mac 固件上关

C 组 · KASLR slide 与低位内存（「放不下内核」那一类）

内核要被装进低 4 GB 里，位置是随机挑的（叫 slide）。固件把低位内存占得七零八落时，随机挑到「不能用」的值就直接启动失败——表现是时好时坏、随机卡住。

开关一句人话Sample 值
ProvideCustomSlide先分析地图，只从真正可用的 slide 里挑。判定信号：日志 OCABC: Only N/256 slide values are usable!开
EnableSafeModeSlide安全模式会强制 slide=0，这个打补丁让它也能用别的值。必须先开 ProvideCustomSlide开
ProvideMaxSlide整数（0／1–254），给 slide 上限封顶；随机启动失败时用。必须先开 ProvideCustomSlide0
AllowRelocationBlock低端内存被占满时，在低 4 GB 之内另找一块暂存缓冲装内核，内核启动前再拷回原本的低地址。通常需要 ProvideCustomSlide + AvoidRuntimeDefrag；官方末句：仅在确实需要时才会使用重定位块——启用 quirk 只是留一条退路，不等于每次启动都放弃休眠。与 macOS 11 及部分硬件不兼容关
DevirtualiseMmio把 MMIO 区域的「运行时」属性摘掉，能腾出 64–256 MB、增加可用 slide。某些板子不开就根本起不来（分配错误）。很老的 Sandy Bridge 除外关
MmioWhitelist（数组）开了 DevirtualiseMmio 后，把 NVRAM / 休眠仍需要虚拟地址的那几个地址单独加回白名单空

D 组 · 不在 A–C 组里，却强耦合的开关

开关和什么耦合
FixupAppleEfiImagesMisc → Security → SecureBootModel。官方：SecureBootModel = Disabled 时，所有较新 macOS 都必须开；走 Apple 安全启动路径时不用
ResizeAppleGpuBars整数。-1 关闭，0 是唯一受支持的值（把显卡 BAR 缩到最小）。与 UEFI → ResizeGpuBars 联动，见 R7
ProtectSecureBoot阻止系统写 db/dbx/PK/KEK；针对 NVRAM 有碎片问题的固件（MacPro5,1、部分 Insyde）
DisableSingleUser / SignalAppleOS / ProtectSecureBoot 等不属于内存映射，别在排查卡住时乱动
03

耦合关系图

三种关系，颜色区分：互斥 绝对不能同时开；前置 前者开了后者才有意义；保障 前者保护后者不被固件冲掉。

图 2 · 三类耦合：互斥（红）、前置（蓝）、保障（绿）
图 2 中①是最容易配错的一条。很多人把 EnableWriteUnprotector 和 RebuildAppleMemoryMap 一起开，以为「双保险」。官方写的是前者被后者取代，同时开属于重复修补同一件事，反而可能引入权限冲突。判定依据很明确：看调试日志里的 OCABC: MAT support is 1/0。
04

十二条硬规则

这些是官方文档里写明、不依赖机型偏好的确定关系，可以直接当规则库用。

R1
互斥：RebuildAppleMemoryMap ↔ EnableWriteUnprotector固件支持 MAT（日志 OCABC: MAT support is 1）→ 开 Rebuild、关 EnableWriteUnprotector；不支持 → 反过来。官方原话：前者「取代」后者。
R2
常成对：RebuildAppleMemoryMap ＋ SyncRuntimePermissions官方注 1：不少固件的内存保护表本身是错的，所以这个 quirk 常与 Sync 一起出现。Sync 的适用信号官方写的是「早期引导失败，既包括黑屏挂起、也包括更明显的崩溃」，且通常只影响 2017 年后发布的固件——别把「有崩溃栈」一律当成排除这一组的理由。
R3
保障：ProtectUefiServices → 三个内存管理 quirkVMware、部分现代固件、以及经 GRUB 链式加载时，固件会改 UEFI 服务指针，直接让 DevirtualiseMmio / ProtectMemoryRegions / RebuildAppleMemoryMap 失效。这些场合先开 ProtectUefiServices。
R4
前置：ProvideCustomSlide → EnableSafeModeSlide / ProvideMaxSlide / AllowRelocationBlock前两个官方明确写「requires enabling ProvideCustomSlide」；AllowRelocationBlock 通常还需要 AvoidRuntimeDefrag 一起开。
R5
连带：DevirtualiseMmio → 可能要 MmioWhitelist摘掉 MMIO 的运行时属性后，某些固件需要把 NVRAM / 休眠仍要用到的地址单独列进白名单，否则时间、NVRAM、休眠会出问题。条目要求该地址属于内存映射中的 EfiMemoryMappedIO 且带有 EFI_MEMORY_RUNTIME 属性，候选地址可从调试日志里找；Sample.plist 自带两条默认禁用的示例（Haswell 的 SB_RCBA、通用 PCI root）。
R6
跨区：SecureBootModel = Disabled → FixupAppleEfiImages 必须开官方：所有较新 macOS 在 SecureBootModel 为 Disabled 时都需要它；走 Apple 安全启动路径时不施加。
R7
跨区：ResizeAppleGpuBars ↔ UEFI → ResizeGpuBars / ResizeUsePciRbIoResizeAppleGpuBars 只支持 -1（禁用）和 0（缩到最小 BAR）；ResizeGpuBars 是全局 BAR 设置，两者都由 ResizeUsePciRbIo 决定用 PciIo 还是 PciRootBridgeIo（老平台改 ReBarUEFI 报 Capability I/O Error 时切后者）。
R8
近乎通用：AvoidRuntimeDefrag官方：「除 Apple 和 VMware 外，大多数固件都需要这个 quirk」。这一项基本不用纠结，PC 上开着就行。
R9
不兼容：SetupVirtualMap × 32 位内核官方 Note 2 明确不兼容；只影响跑老系统的场合。
R10
有条件的兜底：AllowRelocationBlock，不是「开了就废掉休眠」官方末句：启用该 quirk 时，仅在必要时才会使用重定位块。三个触发条件（无更好的 slide、强制 slide=0、10.7 及更早不支持 KASLR）都不满足时，它只是静静地留一条退路；只有真的用到它启动，才不支持休眠。因此「适用条件不满足」≠「必须关闭」。真正要关的是另一种情况：在 macOS 11 或某些硬件上出现兼容冲突，此时官方建议改用 EnableSafeModeSlide。
R11
总前提：OpenRuntime.efi官方排错问答：「大多数配置都需要 OpenRuntime 驱动」；EnableWriteUnprotector、ClearTaskSwitchBit、DisableVariableWrite 等都明确要求其中的 OC_FIRMWARE_RUNTIME 协议。驱动没加载，这些开关全是空转。
R12
别乱开：DiscardHibernateMap / ForceExitBootServices两处都写着「不理解后果不要使用」，官方还说这两个「很少真正需要」。它们属于特定老硬件的救命选项，不是排查卡住时的常规尝试项。

06

症状 → 该动哪个

卡住时先记下屏幕上最后一行或调试日志里最后几条，再按这张表定位。从上往下匹配，越靠前越早死。

看到的现象 / 日志属于哪一层该动哪个开关
黑屏、无苹果标、立刻重启，几乎没有任何输出 ② 权限标注 SyncRuntimePermissions → 再试 SetupVirtualMap 取反 → 再试 RebuildAppleMemoryMap。官方明确把「黑屏卡住」列为 Sync 的适用信号
卡在 [EB|#LOG:EXITBS:START] 或 EndRandomSeed ③ 地址与空位 先确认 ProvideCustomSlide 开着；再看 DevirtualiseMmio（腾出低位内存）；必要时 MmioWhitelist

PCI 初始化阶段卡住 / Capability I/O Error 显卡 BAR（跨区） UEFI → ResizeGpuBars、Booter → ResizeAppleGpuBars、ResizeUsePciRbIo（R7）
某个 PCIe 设备整体不枚举：系统报告里该硬件端口为空、IORegistry 找不到设备 ID、硬件端口列表少了一项 固件 / 设备层，不是这一组 先查 BIOS 里的板载设备开关（Onboard LAN / Controller 等）与固件设置是否被重置，再看设备是否被 ACPI 屏蔽。内存映射 quirk 不会让一个 PCIe 设备从配置空间里消失
系统能起来，但只显示基础帧缓冲 / 某个驱动不工作 驱动层，不是这一组 查 kext 是否加载、IOKit 是否建立实例、有无 panic 栈。这类失败发生在「交接」完成之后
崩点明确落在第三方 kext / 存储栈的完整 panic 栈、禁止符号、Still waiting for root device 通常不是这一组 转向 kext / ACPI / 存储驱动排查。但注意 R2：早期引导崩溃也可能是 Sync 的信号，若崩点不明且反复出现，仍要回头试这一组
一次只改一个。官方排错问答的原话是「逐个检查 Quirks」，并承认那 5 个没有确定方法、可能要试各种组合。同时改三个开关，就算碰巧能开机，你也不知道是哪个起了作用，下次换系统版本又会踩回去。把每套组合存成独立配置文件、开机时直接选择，比反复改同一个文件更安全，也更容易回退。
07

排错顺序

  1. 先取证，判归属，再决定要不要碰这一组：能拿到 panic 栈就看崩点；设备树里连设备都枚举不到就查固件；只有日志停在内核打印第一条错误之前、反复黑屏或立刻重启，才进入本组。DEBUG 构建可开 Misc → Debug → SysReport——OpenCore 在把控制权交给内核之前就会把 ACPI、SMBIOS 等固件表转储到 ESP 的 SysReport/，即使后续黑屏也拿得到现场（RELEASE 构建没有此选项）。
  2. 先把调试打开，否则后面全是盲猜：Misc→Debug→AppleDebug / ApplePanic / DisableWatchDog = 开、ShowPicker = 开，boot-args 加 -v debug=0x100 keepsyms=1。日志落不下来时用串口或 UEFI Shell 看早期输出。
  3. 确认前提：OpenRuntime.efi 在 UEFI→Drivers 里且已加载（R11）。这一步没过，下面全白试。
  4. 先定路线：查 OCABC: MAT support，按 R1 决定 Rebuild 还是 EnableWriteUnprotector，并按 R2 决定是否配 Sync。
  5. 再定底座：VMware / GRUB 链式加载 / 现代固件改服务指针的场合，开 ProtectUefiServices（R3）。
  6. 再定 slide：ProvideCustomSlide 及其两个下游（R4）；出现分配错误才动 DevirtualiseMmio 和 MmioWhitelist。
  7. 最后才试那 5 个没有通解的：Rebuild / EnableWriteUnprotector / ProtectMemoryRegions / SetupVirtualMap / SyncRuntimePermissions，一次一个、组合逐个过。
  8. 每次只改一个、记下来、重启验证；稳定后把组合固化成一个独立 config，别在能开机的配置上继续「优化」。
08

口径与出处

  • 条目依据 OpenCore 1.0.8 官方文档 Docs/Configuration.tex 的 Booter → Quirks Properties 章节、Troubleshooting → How can I decide which Booter quirks to use? 问答，以及中文《OpenCore 配置参考手册 1.0.8》第 5.5 节与第 12.5 节。中英文措辞有出入时以英文原文为准（本次即据此更正了重定位块的位置）。
  • 「安全值（Failsafe）」与「Sample 值」的区别见第 02 节；第 02 节表格的对照列取自 Docs/Sample.plist，不是推荐值。
  • 文中「开／关」对应 plist 布尔 true／false；整数项（ProvideMaxSlide、ResizeAppleGpuBars）单独标注了取值。
  • 「试」表示该场景官方未给定解、需要逐个组合验证；第 05 节表格是快速索引，具体判定仍以第 04 节硬规则和调试日志为准。
  • 本指南为通用排错参考与规则底稿，不绑定任何具体机型或某一份 config.plist。套用到具体机器时请另做逐项比对，并保留可回退的配置副本。
